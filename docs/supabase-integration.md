# Supabase persistence integration

ASTHA keeps its existing Bangla/English PWA, Capacitor applications, Express API, spoken PIN accounts and JWT sessions. Supabase provides PostgreSQL persistence behind that API. Maira remains the separately configured AI provider; its credentials cannot authenticate to Supabase.

The selected dashboard project is [mivbubfefixkghrogkma](https://supabase.com/dashboard/project/mivbubfefixkghrogkma). Authenticated dashboard metadata inspection succeeded on 11 October 2026: Healthy status, free Nano compute in Tokyo, an existing public.asha_objects table (path/text, value/jsonb, updated_at/timestamptz), no astha schema in the schema selector and no astha_backend role in the role list. The existing table shows RLS enabled, API disabled and no policies. Personal rows/counts were not inspected. The Connect dialog confirmed the direct host and session pooler; no database password was read or saved. No schema, data import, role provisioning or deployment was performed.

## Existing behavior and smallest migration

`server/db.js` originally opened Node's built-in SQLite database and exposes synchronous `run`, `get` and `all` helpers. The branch preserves that development path and adds the explicit Supabase adapter. PostgreSQL queries are asynchronous and use different parameter binding. The adapter and its callers in `server/auth.js`, `server/index.js`, `server/memory.js`, `server/rag.js` and `server/agent.js` now await results and forward failures through Express's error handler. Preserve HTTP paths, response fields, input limits, per-user filters and offline client behavior. A PostgreSQL outage must not silently select a different SQLite database or turn a database error into an invalid-login response.

The schema preserves all six existing tables: `users`, `memories`, `rooms`, `events`, `agent_tasks` and `knowledge_docs`. IDs remain TEXT nanoids, PIN hashes/salts and JSON fields remain TEXT, and recognition scores use DOUBLE PRECISION. Millisecond timestamps require BIGINT; normalize returned timestamp values to safe JavaScript numbers so API responses and recency ranking remain compatible. Converting JSON columns to JSONB immediately would change parsing behavior. [Node Postgres type handling](https://node-postgres.com/features/types).

Keep scrypt PIN verification, account IDs, normalized/legacy phone handling and the existing JWT signing secret. This preserves existing sessions when their account records are imported. The application `astha.users` table is independent from Supabase Auth's `auth.users`. Replacing accounts with Supabase Auth or assigning new UUIDs is a separate identity migration; it is unnecessary for this persistence change.

## Private schema and trusted backend role

[`server/migrations/001_supabase.sql`](../server/migrations/001_supabase.sql) is an explicit, one-time migration. Application startup must never apply it or create tables. It runs in a transaction and refuses any existing `astha` schema instead of silently accepting incompatible tables or replacing data. Review an existing schema and migration history before choosing a subsequent migration.

Provision `astha_backend` separately as a LOGIN role with no SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS or memberships in other roles. Set its password through a protected administrative process; no application password belongs in this migration or repository. Apply the migration with a distinct schema-owner role, using a protected database service configuration and `psql -v ON_ERROR_STOP=1 -f server/migrations/001_supabase.sql`.

The migration grants `astha_backend` only schema USAGE and SELECT/INSERT/UPDATE/DELETE on the six application tables. It cannot create schema objects and must not own the schema or tables. All six tables have enabled and forced RLS, with a single policy admitting the backend role. PUBLIC, anon, authenticated and service_role receive no access or policies; revokes for Supabase roles are conditional so the migration also runs on generic PostgreSQL.

These policies authorize the trusted backend to access application tables. They do not enforce individual account ownership inside PostgreSQL. Express must verify every ASTHA JWT and retain every `user_id`/owner condition on reads and writes. Test cross-account reads, deletes and updates through the API. Never use a Supabase administrative key as a replacement for those checks.

Keep `astha` out of the Data API's exposed schemas. If this project has other applications, do not change their schemas or grants. If this project does not need any REST/GraphQL Data API access, disabling that API is an additional reviewed project setting. Browser-facing data access requires a separately designed identity/RLS integration. [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api).

The schema comment is the fixed version marker `astha-schema-v1`; no seventh metadata table is introduced. Startup reads that comment and verify the six expected table/column definitions, role identity/privileges and schema ownership before listening. It rejects incompatible or incomplete schemas and reject owner/BYPASSRLS application connections.

The fresh PostgreSQL schema has the unique index `idx_rooms_user_name` on `(user_id, lower(name))`. Room saves use one atomic `INSERT ... ON CONFLICT (user_id, lower(name)) DO UPDATE ... RETURNING id`, preserving the existing room ID and name while updating notes and time. Startup also verifies that this index is unique, valid and has the expected definition. SQLite retains a single synchronous `saveRoom` operation; this change does not install an index or clean duplicates in an existing SQLite database.

## Connections, secrets and hosting

Use a server-only PostgreSQL connection string for the limited application role. Copy the correct host/port from the selected project's Connect dialog. A persistent IPv6 backend can use a direct connection; IPv4-only persistent backends can use the shared session pooler. Transaction pooling is intended for serverless/Edge workloads and requires compatible driver settings, including disabled named prepared statements and no reliance on session state between transactions. Use a bounded application pool, timeouts and verified TLS certificates. Do not purchase an IPv4 add-on or change project plans during setup. [Supabase connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

| Server configuration | Contract |
| --- | --- |
| `DB_PROVIDER` | `sqlite` is the development/default path; `supabase` selects PostgreSQL explicitly. |
| `SUPABASE_DB_URL` | Server-only PostgreSQL URL for `astha_backend`; shared-pooler usernames have the form `astha_backend.<project-ref>`. Use the host from Connect. No URL query arguments are accepted. |
| `SUPABASE_DB_CA_FILE` | Optional local path to the server's trusted CA certificate. Server identity verification remains enabled. |

The PostgreSQL adapter uses at most five pool connections, a five-second connection deadline, ten-second statement deadline and twelve-second client query deadline. URL options cannot override TLS verification; insecure SSL options are rejected. With `DB_PROVIDER=supabase`, missing configuration or a failed role/schema/connection check must stop startup, without selecting SQLite.

Database passwords and Supabase secret/service-role keys stay in server secret storage. They must never enter `web/config.js`, generated HTML, APK/IPA assets, logs or health responses. Publishable keys identify an application; they do not authenticate ASTHA's existing PIN users. Secret keys bypass RLS and belong only in trusted backends. This database-only path needs no Supabase key in the frontend. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).

Supabase PostgreSQL does not host the current long-running Express process. The HTTP API still needs an explicitly selected Node/container host. `render.yaml` currently requests a paid starter service and persistent disk; do not deploy it or infer spending authorization from selecting Supabase. `Dockerfile` currently prepares `/data/astha.db`. Remove a SQLite disk requirement only after a verified persistence cutover, preserving the old database and its backups.

Supabase Edge Functions are a later service migration. They use a Deno-compatible runtime with npm/Node compatibility, and the documentation includes Express; an Express dependency alone does not make the application unsupported. However, the existing Node 24 startup, `node:sqlite` DatabaseSync, synchronous hashing, auth middleware and speech streaming require runtime-specific validation. The documented temporary filesystem resets per invocation; persistent S3 mounts do not establish SQLite WAL, file locking or concurrent writer guarantees. Keep relational state in Postgres. [Edge dependencies](https://supabase.com/docs/guides/functions/dependencies), [function file storage](https://supabase.com/docs/guides/functions/ephemeral-storage), [runtime limits](https://supabase.com/docs/guides/functions/limits).
